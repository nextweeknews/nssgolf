# Repository operating rules

These rules apply to the entire repository. `main` is the production source. Development happens on short-lived feature branches in the isolated local environment; releases use a reviewed pull request and an agent-managed, backend-first production sequence after explicit approval.

## Non-negotiable safety

- Never commit or push directly to `main`. Fetch `origin`, branch from the current `origin/main`, and merge only through a reviewed pull request.
- Never merge, deploy, dispatch a production workflow, or perform another remote write unless the user explicitly approves the complete production release in the current task. Implementation or local-testing permission is not release permission.
- Before editing, inspect the current branch and `git status`. Preserve unrelated user changes and keep each branch and PR limited to one requested scope.
- The Supabase Dashboard, Supabase MCP, browser automation, and remote SQL editors are read-only inspection tools. Production SQL changes are deployed only from committed migrations with the local Supabase CLI.
- Never expose or copy credentials. Before reporting missing GitHub or Supabase authentication, run `gh auth status`, or `supabase --help` followed by `supabase projects list`, so the native CLI can use macOS Keychain. If the sandbox blocks the check, request permission and retry before asking the user to authenticate.
- Never run a bot, scanner, replay, import, or synchronization command against production merely to validate code. Use unit tests and the synthetic local environment unless the release scope explicitly requires the production operation.

## Sources of truth

- Repository application, bot, Worker, workflow, and configuration files are authoritative; production is a deployment target, not an authoring environment.
- Ordered files in `supabase/migrations/` are the source of truth for linked database schema, RLS, grants, functions, triggers, and controlled deployment data. Create changes with `supabase migration new <descriptive_name>` and never edit, rename, delete, squash, or reorder an applied migration. Correct it with a new forward migration.
- `supabase/config.toml` and `supabase/seed.sql` configure the isolated local stack. Local Auth users, synthetic Discord records, seed rows, containers, networks, and volumes are never promoted to production.
- `worker/` is the source for the `small-mud-2771` Cloudflare Worker. Keep secrets in Cloudflare; never place secret values in `wrangler.jsonc`, browser code, logs, or commits.
- The linked Supabase project is `kwaprkwemtxizorpnrzq`. Stop if `supabase projects list` or linked metadata identifies a different target.

## Local testing environment

- The project uses Supabase project ID `nssgolf`, Docker network `nssgolf-local`, ports `54520`-`54529`, and the static site at `http://127.0.0.1:8080`. Do not reuse another repository's project ID, network, ports, or containers.
- `npm run dev:reset` starts the project-scoped stack, replays every migration, loads synthetic fixtures, creates synthetic admin/player Auth users, attaches canonical Discord identities, and verifies fixture coverage.
- `npm run dev` serves the current branch with an injected local Supabase URL and publishable key. Open `http://127.0.0.1:8080/__local/login` to enter as the synthetic admin or player. The login helper is generated by the local server and is not a deployable website asset.
- `npm run dev:verify` checks fixture integrity. `npm run dev:check` runs database tests, lint, and advisors. `npm run dev:smoke` proves the site uses local Supabase, repository-private files are not served, public fixtures load, and admin/non-admin authorization remains separated.
- `npm run dev:stop` stops only project ID `nssgolf` and preserves its data volume. Never use `supabase stop --all`, broad Docker deletion, or `--no-backup` for normal shutdown. Inspect active containers before lifecycle changes if another repository may be running.
- Keep deployable work in source files. A change made only in local Studio or the local database is not a production change.

## Local development to production promotion

1. **Start from production and branch before editing.** Inspect the worktree, fetch `origin`, and create a short-lived `codex/<scope>` branch from current `origin/main`. There is no long-lived development branch.
2. **Develop locally.** Use `npm run dev:reset` when data, Auth, RLS, migrations, or admin behavior matters; use `npm run dev` for browser acceptance. Leave an intentionally started user-testing server running unless the user asks to stop it or it fails.
3. **Classify the diff.** Application/assets/content only release through Pages. Database changes require a new forward migration. Discord data-shape or role-authorization changes may require the member scan. `worker/` changes require a Worker deployment. The Fly app is the long-running Discord global-ranks bot, so deploy it only when its bot, package, or container source changed. Ranking-data jobs may require the Internal Ranked workflow only when explicitly included.
4. **Validate locally.** Run `npm test`, `npm run build`, and affected browser checks. For Supabase-related changes also run `npm run dev:reset`, `npm run dev:check`, and `npm run dev:smoke`. Review `git diff --check` and the complete diff against `origin/main`.
5. **Promote through a PR.** Commit only the scoped files, push the feature branch, and open a PR to `main`. Require green `Application checks` and `Supabase migration checks`, a conflict-free exact head, primary review, and the independent subagent review below.
6. **Obtain explicit approval.** Summarize the exact PR head, validation, review findings and dispositions, database/Discord/Worker/web scope, and release order. Ask the user to approve both merge and the complete production release. A changed PR head requires renewed review and approval.
7. **Release backend first from reviewed source.** Merge the approved PR, fast-forward a clean local `main` to the exact merge commit, verify the linked Supabase target/history/dry-run, then deploy only changed backend components in this order: migrations; required Discord member scan; `small-mud-2771` Worker; Fly-hosted global-ranks bot. Application-only changes perform no Supabase, Discord, Worker, or Fly write.
8. **Release web surfaces.** Only after backend verification, dispatch the manually gated GitHub Pages workflow from `main` with `backend_verified=true`. Dispatch Internal Ranked only when it is part of the approved scope. Monitor every run to completion.
9. **Verify and clean up.** Smoke-test `https://www.nssgolf.com/`, affected routes, Worker endpoints, and production data boundaries as applicable. Report the exact commit and component versions, delete merged branches, and finish on clean local `main` matching `origin/main`.

## Pull request and independent review

- Before the first push, inspect all intended files and confirm that local fixtures, credentials, generated outputs, and unrelated work are absent from the commit.
- Once a Codex-authored PR is complete and green, assign a dedicated subagent a bounded, read-only review of the complete PR diff plus relevant callers, tests, migrations, policies, Worker routes, and workflows. The task must explicitly look for functionality gaps, security concerns, scope overreach, and regressions. The subagent must not edit files or perform remote writes.
- The primary agent evaluates every finding. Fix actionable findings on the feature branch, rerun the affected local gates, update the PR, and request a new exact-head subagent review. Never ask for merge approval while actionable findings remain or the agents disagree about readiness.
- If a second review after fixes proposes more edits, stop and ask the user whether to release as-is, make one selected targeted edit and release without a third review, or continue the review loop.
- The approval request must report the subagent task, findings, primary-agent dispositions and resulting changes, non-actionable considerations or disagreements, and final agreement. If subagents are unavailable, disclose that and obtain explicit permission before proceeding without independent review.

## Database and authorization changes

- Rebuild from the complete migration history with `npm run dev:reset`; do not prototype writes against the linked database.
- Before production, run `supabase migration list --linked` and review `supabase db push --linked --dry-run`. Stop on unexplained history differences or unexpected migrations. Never run `supabase db reset --linked`, `supabase migration repair`, `supabase db push --include-all`, or deploy seeds without separate incident-level approval.
- After an approved migration push, require aligned migration history and an empty second dry-run. Run relevant read-only production checks and security advisors.
- Treat grants, RLS policies, column privileges, and RPC `EXECUTE` as separate authorization layers. Public visibility never implies public editability. Authorization uses canonical `auth.identities`, live sessions, synchronized Discord membership/role generations, and server-enforced predicates—not mutable profile or user metadata.
- Keep schema changes compatible with both old and new clients during rollout. Use expand/migrate/contract releases for breaking changes.

## Ordered production components

- **Supabase migrations:** deploy only reviewed pending files with `supabase db push --linked`, then verify history and an empty dry-run.
- **Discord member scan:** when the approved database/authorization change requires a fresh role-assignment generation, confirm the `github-pages` environment permits the exact release ref, dispatch `.github/workflows/discord-member-scan.yml`, and monitor it. Never bypass environment protection. If it cannot run safely before dependent components, stop and report the ordering conflict.
- **Cloudflare Worker:** when `worker/` changed, run its tests first, then deploy the exact reviewed source with `npx wrangler deploy --config worker/wrangler.jsonc`. Smoke CORS, unauthenticated rejection, validation, intended public reads, and affected authenticated writes. Do not create preview deployments or expose Worker secrets.
- **Fly global-ranks bot:** when the approved diff changes its `bot/`, package, Docker, or Fly source, dispatch `.github/workflows/fly-deploy.yml` on `main` with `backend_verified=true` after its database prerequisites pass. Smoke the bot's startup/health behavior and monitor with `gh run watch <run-id> --exit-status`. Do not redeploy Fly for an unrelated website change.
- **GitHub Pages:** dispatch `.github/workflows/pages.yml` on `main` with `backend_verified=true` only after all required backend components pass verification. Monitor with `gh run watch <run-id> --exit-status`.
- **Internal Ranked:** scheduled production data jobs are not a routine web-release step. Dispatch only the named, approved operation with reviewed inputs and monitor it to completion.

## Prohibited shortcuts

- No direct commits to `main`, force pushes, branch-protection bypasses, auto-merge before approval, or deployments from a dirty/unreviewed worktree.
- No remote SQL, Dashboard edits, MCP writes, browser writes, seed promotion, or production data copies as substitutes for migrations and synthetic fixtures.
- No Pages dispatch before required Supabase, Discord, Worker, and Fly deployment and verification; no Fly dispatch before its own database prerequisites.
- No ad hoc production bot runs, broad container shutdowns, secret retrieval into output, or replacement of existing credential stores with plaintext token files.
